5.0 Null Hypothesis คืออะไร — ก่อนอ่านค่า p ใดๆ

ตั้งแต่บทที่ 4 เล่มนี้เริ่มพูดถึง p-value และ ADF โดยยังไม่เคยหยุดอธิบายว่ามันวัดอะไรกันแน่ — ก่อนไปต่อกับ cointegration ต้องหยุดตรงนี้ก่อน เพราะทุกการทดสอบสถิติที่เหลือทั้งเล่ม (ADF, KPSS, Shapiro-Wilk, Johansen) วางอยู่บนตรรกะเดียวกันหมด

อุปมา — ศาลตัดสินคดี: "จำเลยบริสุทธิ์ไว้ก่อน"

สมมติฐานหลัก (H₀ — null hypothesis) คือจุดตั้งต้นที่เรา สมมติว่าเป็นจริงไว้ก่อน จนกว่าจะมีหลักฐานหนักแน่นพอจะ "ปฏิเสธ" มัน — เหมือนศาลที่ต้องสมมติว่าจำเลยบริสุทธิ์ (H₀) จนกว่าอัยการจะมีหลักฐานเพียงพอ (data) มาหักล้าง ถ้าหลักฐานไม่พอ ศาลไม่ตัดสินว่าบริสุทธิ์จริง — แค่บอกว่า "หลักฐานไม่พอจะเอาผิด" เท่านั้น การทดสอบสถิติก็เช่นกัน: ไม่ reject H₀ ≠ พิสูจน์ว่า H₀ จริง แค่แปลว่าข้อมูลที่มีไม่พอจะปฏิเสธมัน

1
ตั้ง H₀ (null) และ H₁ (alternative):
H₀ = สมมติฐาน "ไม่มีอะไรพิเศษเกิดขึ้น" (สถานะเริ่มต้นที่อนุรักษ์นิยม) — H₁ = สิ่งที่เราสงสัยว่าอาจเป็นจริง
2
คำนวณ test statistic จากข้อมูลจริง แล้วถามว่า "ถ้า H₀ เป็นจริง โอกาสที่จะเห็นข้อมูลสุดขั้วเท่านี้ (หรือมากกว่า) คือเท่าไร"
3
ค่านั้นคือ p-value — ถ้าเล็กมาก (ต่ำกว่า threshold เช่น 0.05) แปลว่าข้อมูลที่เห็น "ไม่น่าจะเกิดขึ้นได้" ถ้า H₀ เป็นจริง → เรา reject H₀
p-value แปลว่าอะไร

p-value = P(เห็นข้อมูลสุดขั้วเท่านี้หรือมากกว่า | สมมติว่า H₀ เป็นจริง) — เป็นข้อความเกี่ยวกับข้อมูลภายใต้สมมติฐาน ไม่ใช่ข้อความเกี่ยวกับความน่าจะเป็นที่ H₀ จะจริง

p-value ไม่ได้แปลว่าอะไร (ความเข้าใจผิดที่พบบ่อยสุด)
  • ไม่ใช่ "โอกาสที่ H₀ เป็นจริง" — p = 0.03 ไม่ได้ แปลว่า "มีโอกาส 3% ที่คู่นี้ไม่ cointegrated" (นี่คือ P(H₀|data) ซึ่งเป็นคนละปริมาณกับ p-value = P(data|H₀))
  • ไม่ใช่ "ความน่าจะเป็นที่ผลลัพธ์เกิดจากบังเอิญ" ในความหมายกลับด้าน
  • ไม่ใช่ ตัววัดขนาดของ effect — p ต่ำมากไม่ได้แปลว่า edge ใหญ่ (sample ใหญ่พอ p จะต่ำได้แม้ effect เล็กจิ๋ว)
  • p ≥ 0.05 ไม่ใช่ หลักฐานว่า H₀ จริง — อาจเป็นเพราะ sample เล็กเกินไปจน test ไม่มีกำลังมองเห็นความแตกต่าง (ดู "Power" ด้านล่าง)
กับดักเฉพาะของ ADF — ทิศทางที่คนอ่านกลับกันบ่อยที่สุด

สัญชาตญาณทั่วไปมักคิดว่า "p ต่ำ = แย่, p สูง = ดี" (เช่น p-value ของยาที่ไม่ได้ผล) แต่ ADF สลับทิศ:

H₀ ของ ADF = "มี unit root" (ε ไม่ stationary — เดินสุ่มไม่กลับค่ากลาง)

ดังนั้น p ต่ำ = reject H₀ = ε stationary = ข่าวดี (cointegrated, เทรดได้) — สลับกับสัญชาตญาณทั่วไปโดยสิ้นเชิง ผู้อ่านที่เจอ "p = 0.02" แล้วคิดว่า "แย่จัง มีแค่ 2%" จะตีความกลับด้านทันที กฎจำง่าย: สำหรับ ADF ให้คิดว่า p ต่ำ = ผ่าน เหมือนสอบ (ตรงข้ามกับ KPSS ที่ H₀ = stationary — p สูงถึงจะผ่าน ดู บทที่ 6 §6.3)

ในการ scan หาคู่เทรดหลายร้อยคู่ Type I Error คือตัวที่อันตรายกว่า — เทรดคู่ปลอมด้วยเงินจริงเสียหายทันที ขณะที่พลาดคู่ดี (Type II) แค่เสียโอกาส ไม่เสียเงิน ธนาคาร/บทนี้จึงเน้น significance level (α) ต่ำ (0.05 หรือต่ำกว่า) เพื่อควบคุม Type I Error ก่อน

Power ของ Test — ทำไม Sample สั้นถึงอันตราย

Power = โอกาสที่ test จะ reject H₀ ถูกต้อง เมื่อ H₁ เป็นจริง (1 − P(Type II Error)) — power ต่ำเมื่อ sample เล็ก แปลว่า: ถ้าใช้ lookback สั้น (เช่น 20-30 bar) แล้ว ADF ไม่ reject H₀ อาจไม่ใช่เพราะคู่นี้ไม่ cointegrated จริง แต่เพราะ test ยังไม่มีกำลังพอจะตรวจจับมัน (power ต่ำ) — นี่คือเหตุผลที่ §3.10 และ บทที่ 4 §4.4 เตือนเรื่อง lookback สั้นซ้ำแล้วซ้ำเล่า: window สั้นไม่ใช่แค่ estimate ไม่แม่น แต่ทำให้ test เชื่อถือไม่ได้ทั้งสองทิศ (ทั้ง false positive จาก overfit และ false negative จาก power ต่ำ)

โยงเข้า Multiple Testing — ทำไม scan หลายคู่ต้องระวังเป็นพิเศษ

ทุกครั้งที่ทดสอบ H₀ หนึ่งครั้งที่ α=0.05 มีโอกาส 5% ที่จะ reject ผิด (Type I) แม้ H₀ จะจริง — ถ้า scan 100 คู่พร้อมกัน (100 tests อิสระ) คาดว่าจะมีคู่ปลอมที่ "ดูเหมือน" cointegrated โดยบังเอิญประมาณ 5 คู่ แม้ไม่มีคู่ไหนมี edge จริงเลยสักคู่ — นี่คือเหตุผลที่ บทที่ 4 §4.4 เตือนว่า "ลอง 5 window แล้วเลือกที่ดีที่สุด" เพิ่ม false positive rate ขึ้นตาม family-wise error rate ไม่ใช่คงที่ 5% เหมือนทดสอบครั้งเดียว — วิธีแก้เบื้องต้น: ลด α ตามจำนวน test (Bonferroni correction: α/n) หรือดีกว่านั้นคือ out-of-sample validation เสมอ (walk-forward, §3.9)

โจทย์ 5.0 — ตีความ p-value ให้ถูกทิศ

เพื่อนบอกว่า "ADF test ของคู่ BTC/ETH ได้ p-value = 0.08 ดังนั้นมีโอกาส 92% ที่คู่นี้ cointegrated จริง เทรดได้"

ถาม: คำพูดนี้ผิดตรงไหน อธิบาย 2 จุด

ดูคำตอบ

ผิดจุดที่ 1 — ตีความ p-value เป็นความน่าจะเป็นของ H₀: p-value ไม่ใช่ P(cointegrated | data) แต่คือ P(เห็นข้อมูลแบบนี้ | ไม่ cointegrated) การพูดว่า "92% cointegrated" คือเอา 1−p ไปตีความผิดประเภทของความน่าจะเป็นทั้งหมด

ผิดจุดที่ 2 — p ≥ 0.05 ไม่ reject H₀ ไม่ได้แปลว่าเทรดได้: p=0.08 คือ "ไม่มีหลักฐานพอจะปฏิเสธว่าไม่ cointegrated" — เท่ากับศาลบอกว่าหลักฐานไม่พอเอาผิด ไม่ใช่ "บริสุทธิ์แน่นอน" ที่ถูกต้องคือไม่ควรเทรดคู่นี้ (หรืออย่างน้อยต้องหาหลักฐานเพิ่ม เช่น เพิ่ม sample size แล้วทดสอบใหม่)

แก่นของบทนี้ — ADF Equation

Correlation สูงไม่พอสำหรับ stat arb — ต้องการ cointegration: ε (สร้างจาก F(·) แบบใดก็ได้ — ดู บทที่ 4B) ต้องเป็น stationary (กลับหาค่ากลาง) ไม่ใช่แค่เดินไปด้วยกัน
ตัวอย่างในบทนี้ใช้รูป default: \(\varepsilon_t = \log A_t - \beta \cdot \log B_t\) — แต่การทดสอบทั้งหมดใช้กับ ε ทุกตระกูล

ADF test ประมาณค่า δ จาก regression นี้:

$$\Delta\varepsilon_t = \alpha + \delta\varepsilon_{t-1} + \sum_{k=1}^{p}\gamma_k\Delta\varepsilon_{t-k} + \eta_t$$

\(H_0{:}\ \delta = 0\) (unit root — ε ไม่ stationary)   \(H_1{:}\ \delta < 0\) (stationary — ε กลับค่ากลาง)
ถ้า p-value < 0.05 → ปฏิเสธ H₀ → \(\delta < 0\) → cointegrated

นิยามทางการ — Cointegration (Engle & Granger, 1987)

Series X_t และ Y_t แต่ละตัวเป็น I(1) (integrated of order 1 — มี unit root, ไม่ stationary) แต่คู่นี้ cointegrated ถ้ามีค่า β ที่ทำให้:

Z_t = X_t − β·Y_t เป็น I(0) (stationary, กลับหาค่ากลาง)

กล่าวอีกนัย: แม้ X_t และ Y_t จะ random walk แยกกัน แต่ทั้งคู่ถูก "ดึง" ไว้ด้วย long-run equilibrium relationship เดียวกัน — spread ε = Z_t จึงไม่ drift ออกไปตลอด

5.1 Correlation ≠ Cointegration — ความแตกต่างที่สำคัญ

อุปมา — คนกับสุนัขและสายจูง (จำได้ง่ายที่สุด)

Correlation ตรวจว่า "คนกับสุนัขเดินไปทางเดียวกันไหม" — ไม่ใช่แค่ตอนเดินตรง แต่รวมตอนเลี้ยวซ้าย เลี้ยวขวา ข้ามถนน ด้วย ถ้าทุกทิศทางยังพ้องกัน = น่าจะมีสายจูง — แต่ยังยืนยันไม่ได้ว่ามีสายจูงจริง เพราะสองคนที่เดินไปห้างเดียวกันโดยบังเอิญก็ correlation สูงได้

Cointegration ตรวจว่า "มีสายจูงเชื่อมกันจริงไหม" — เมื่อสุนัขวิ่งออกไปห่างจากคน มีแรงดึงให้กลับมาไหม? ถ้ากลับมาเสมอ = spread มีแรง mean-revert = cointegrated
จะกลับมาเร็วแค่ไหน ขึ้นกับ ความยาวสายจูง = Half-life (สายสั้น = กลับเร็ว = trade ได้ถี่)

จุดประสงค์ของ threshold ρ ≥ 0.70 คือ ลดจำนวน pair ที่ต้องรัน ADF ไม่ใช่วัดว่าคู่นั้นดีหรือไม่ดี:

  • คู่ที่มี ρ = 0.65 อาจ cointegrate ได้จริง — 0.70 เป็นแค่จุดเริ่มต้น ไม่ใช่เส้นแบ่ง
  • คู่ที่มี ρ = 0.92 อาจ ไม่ cointegrate เลย (spurious correlation ที่เกิดจากทั้งคู่ trend ขึ้นพร้อมกัน)
  • สิ่งที่สำคัญกว่า ρ ณ จุดเดียว: ρ เสถียรข้ามเวลาไหม — ρ = 0.72 ที่คงที่ตลอด 90 วัน มักดีกว่า ρ = 0.88 ที่กระโดดระหว่าง 0.55–0.95

ปรับ threshold ได้ตาม context: มี pair น้อย (≤ 20 คู่) → รัน ADF ทุกคู่เลย ไม่ต้องกรองด้วย ρ ก่อน · มี 200+ คู่ → ใช้ ρ ≥ 0.75–0.80 เพื่อลด compute cost

5.2 Engle-Granger 2-Step Test

วิธีที่ง่ายที่สุด ทำ 2 ขั้น:

1
Regress log(P_A) บน log(P_B):
log(P_A) = α + β·log(P_B) + ε̂_t
บันทึก residuals ε̂_t จาก regression นี้
2
ADF Test บน ε̂_t:
ถ้า ε̂_t stationary (p < 0.05) → A และ B cointegrated ✓
ถ้าไม่ผ่าน (p ≥ 0.05) → ไม่ cointegrated → ห้าม trade

หมายเหตุ: ADF (และ KPSS ที่เป็น test คู่กัน) ใช้ที่นี่เป็นเครื่องมือตัดสิน cointegration — กลไกภายใน สมมติฐาน H₀ และการตีความเชิงลึกของทั้งสอง test อธิบายเต็มใน บทที่ 6

ถ้าคุณ (1) รัน ADF บนข้อมูลทั้งหมด เพื่อเลือกคู่ที่ผ่าน แล้ว (2) backtest บนข้อมูลชุดเดิม — นั่นคือ look-ahead bias: คุณเลือกคู่ที่ "รู้อยู่แล้ว" ว่าผ่าน ซึ่ง backtest จะดูดีเสมอโดยไม่สะท้อน live performance จริง
วิธีป้องกัน: ใช้ walk-forward validation — แบ่งข้อมูลเป็น in-sample (เลือกคู่ + calibrate) และ out-of-sample (backtest) แยกกันเสมอ สัดส่วนที่ใช้บ่อย: 60% in-sample / 40% out-of-sample หรือ rolling window re-test ทุกเดือน

Cutoff มาตรฐาน: p < 0.05 ใช้ได้ในกรณีทั่วไป แต่นักปฏิบัติมักพิจารณาเพิ่มเติม:

  • Window size สำคัญมาก — ข้อมูล < 100 observations ให้ p-value ที่ไม่น่าเชื่อถือ: test มี power ต่ำ ทำให้ fail to reject H₀ แม้ spread จะ stationary จริง · ใช้ ≥ 250 observations ขึ้นไปสำหรับ hourly bars (ประมาณ 10 วัน)
  • p < 0.01 — ควรใช้เป็น threshold สำหรับ position ขนาดใหญ่ (high-conviction)
  • p = 0.05–0.10 (borderline) — ลด position size ลงครึ่งหนึ่ง หรือรอ re-test ด้วยข้อมูลใหม่ ≥ 30 วัน
  • Re-test ทุกเดือน (หรือเมื่อ spread ค้างนอก 3σ > 2 วัน) — cointegration เปลี่ยนตาม regime ของตลาด

แทนที่จะคิดว่า p < 0.05 = "เทรดได้เต็มที่" และ p ≥ 0.05 = "เทรดไม่ได้เลย" ให้ใช้ p-value เป็น confidence score ที่ส่งผลต่อขนาด position โดยตรง:

Model Risk — ADF มี Power ต่ำในตัวอย่างขนาดเล็ก

ADF test มีจุดอ่อนที่สำคัญหลายประการที่ต้องระวัง:

  • Low power เมื่อ sample น้อย — ถ้า n < 100 observations ADF มักจะ fail to reject H₀ แม้ spread จะ stationary จริง ผลลัพธ์คือ "false negative" — ทิ้งคู่ที่ trade ได้จริง
  • Structural break — ถ้า β หรือ equilibrium เปลี่ยนกลางทาง (เช่น event ใหญ่ หรือ delisting) ADF อาจ pass เพราะดู aggregate ที่รวม 2 regime เข้าด้วยกัน
  • Borderline cases ต้องระวังเป็นพิเศษ — p = 0.04–0.06 ไม่มีความต่างทางสถิติที่มีนัยสำคัญ การตัดสินใจจาก threshold ตายตัว (p=0.05) ใน zone นี้มีความเสี่ยงสูง
  • วิธีลด model risk: ใช้ข้อมูลยาวขึ้น + ทดสอบทั้งสองทิศทาง (A~B และ B~A) + ยืนยันด้วย Hurst exponent (บทที่ 6) + re-test ทุกเดือน
ข้อจำกัดของ Engle-Granger
  • Test เพียง 1 cointegrating vector (ดีสำหรับ 2 assets)
  • ลำดับ regression (A บน B vs B บน A) ให้ผลต่างกัน — ควรทดสอบทั้งสองทาง
  • มี power ต่ำเมื่อ sample น้อย (< 100 observations)
⚠️ Engle-Granger Asymmetry — จุดที่ผู้ใช้มักพลาด

สิ่งที่หลายคนเข้าใจผิด: ถ้า regress A~B ได้ β_AB = 1.003 หลายคนคิดว่า regress B~A จะได้ β_BA = 1/1.003 ≈ 0.997 — แต่นั่นผิด

การ regress log(A) ~ log(B) ให้ β_AB = Cov(A,B)/Var(B)
การ regress log(B) ~ log(A) ให้ β_BA = Cov(A,B)/Var(A)

ความสัมพันธ์ที่ถูก: β_AB × β_BA = ρ² (ค่า R²) — ไม่ใช่ 1 อย่างที่คาด
ดังนั้น 1/β_AB ≠ β_BA ทั่วไป (เท่ากันเฉพาะกรณี ρ=1)
และ residual ε_AB กับ ε_BA ต่างกันจริงๆ ไม่ใช่แค่ scale

ผลที่ตามมา: ADF test บน ε_AB อาจ pass (p=0.03) แต่ ADF บน ε_BA อาจ fail (p=0.12) — หรือกลับกัน
วิธีปฏิบัติ: ทดสอบทั้งสองทิศทาง แล้วเลือก β ที่ให้ ADF p-value ต่ำกว่า (residual stationary กว่า)
ถ้าทั้งสองทิศทาง fail → pair ไม่ cointegrate จริง

5.4 VECM — ใครเป็นฝ่ายปรับตัวกลับ?

เมื่อรู้ว่า cointegrated แล้ว VECM (Vector Error Correction Model) บอกว่า เมื่อ spread ห่างจาก equilibrium ใคร (A หรือ B) เป็นฝ่ายปรับตัวกลับ

VECM สำหรับ 2 assets
Δlog(P_A)_t = α_A · ε_{t-1} + γ_A · Δlog(P_A)_{t-1} + u_{A,t}
Δlog(P_B)_t = α_B · ε_{t-1} + γ_B · Δlog(P_B)_{t-1} + u_{B,t}

α_A, α_B = adjustment coefficients — บอกว่าใครปรับตาม error

VECM ระบุว่าควร trade ฝั่งไหน — ถ้า A ปรับ: trade A | ถ้า B ปรับ: trade B | ถ้าทั้งคู่ปรับ: trade ทั้งคู่
VECM บอกอะไรสำหรับ Bybit↔Lighter?

ถ้า Bybit เป็น "price leader" (α_Bybit ≈ 0) และ Lighter ปรับตาม (α_Lighter > 0):
→ เมื่อ Lighter ต่ำกว่า equilibrium: Lighter จะขึ้น → Long Lighter
→ เมื่อ Lighter สูงกว่า equilibrium: Lighter จะลง → Short Lighter
สรุป: trade Lighter เป็นหลัก ใช้ Bybit เป็น reference

5.5 Pseudo-code

# Engle-Granger Cointegration Test
function test_cointegration_eg(log_P_A, log_P_B):
  # Step 1: OLS regression
  beta, alpha = ols(log_P_B, log_P_A) # log_P_A = alpha + beta*log_P_B
  residuals = log_P_A - (alpha + beta * log_P_B)

  # Step 2: ADF test on residuals
  adf_stat, p_value = adf_test(residuals, lags=1)

  cointegrated = p_value < 0.05
  return {cointegrated, p_value, adf_stat, beta, residuals}

# Check VECM adjustment direction
function vecm_adjustment(log_P_A, log_P_B, residuals):
  d_A = diff(log_P_A) # Δlog(P_A)
  d_B = diff(log_P_B) # Δlog(P_B)
  err_lag = residuals[:-1] # ε_{t-1}

  alpha_A = ols_slope(err_lag, d_A[1:]) # A's adjustment coefficient
  alpha_B = ols_slope(err_lag, d_B[1:]) # B's adjustment coefficient

  # Sign logic: ε = log(P_A) - β·log(P_B)
  # ε > 0 → A แพงกว่า equilibrium → A ต้องลง (α_A < 0) · B ต้องขึ้น (α_B > 0)
  # ε < 0 → A ถูกกว่า equilibrium → A ต้องขึ้น (α_A > 0) · B ต้องลง (α_B < 0)
  # A adjusts: α_A < 0 · B adjusts: α_B > 0 (ตรงข้ามกัน เพราะ ε นิยามจาก A−β·B)
  A_adjusts = alpha_A < -0.05
  B_adjusts = alpha_B > 0.05
  return {alpha_A, alpha_B, A_adjusts, B_adjusts}

5.6 Shapiro-Wilk Test — ตรวจ Normality ของ ε

ทำไมต้องตรวจ Normality?
Z-score threshold ±2σ อาศัยสมมติว่า ε ~ Normal distribution — ถ้า ε มี fat tail หรือ skew, threshold นี้จะ underestimate ความเสี่ยง ทำให้เข้า position บ่อยเกินจริง

Shapiro-Wilk test ตรวจสอบว่า sample ε มาจาก Normal distribution หรือไม่:

Hypothesisความหมายผลต่อการ trade
H₀: ε ~ Normalε กระจายแบบปกติใช้ standard z-score (±2σ) ได้ปลอดภัย
H₁: ε ไม่ Normalε มี fat tail / skewใช้ Robust Z-score แทน (MAD-based, ดู บทที่ 10)

Decision Rule

ตัดสินใจจาก p-value
  • p ≥ 0.05: Fail to reject H₀ → normality ไม่ถูก reject → ε likely normal → z-score ±2σ ใช้ได้
  • p < 0.05: Reject H₀ → ε ไม่ normal (fat tail หรือ skew) → ควรใช้ MAD-based robust z-score แทน
from scipy.stats import shapiro def shapiro_test(residuals, alpha=0.05): """ ทดสอบ Normality ของ residuals ε คืนค่า: p_value, is_normal (bool), recommendation """ stat, p_value = shapiro(residuals) is_normal = p_value >= alpha if is_normal: recommendation = "standard_zscore" # ใช้ σ-based threshold ได้ else: recommendation = "robust_zscore" # ใช้ MAD-based (ch10 §10.3) return { "stat": round(stat, 4), "p_value": round(p_value, 4), "is_normal": is_normal, "recommendation": recommendation }
ข้อจำกัดของ Shapiro-Wilk
  • ทำงานได้ดีกับ n ≥ 50 ถึง n ≤ 5,000 — ถ้า n < 50 อาจไม่มีกำลังเพียงพอ; ถ้า n > 5,000 จะ reject H₀ ทุกคู่ (sensitive เกิน)
  • ถ้า n > 5,000: ใช้ D'Agostino K² test หรือดู QQ-plot แทน
  • Fat tail เล็กน้อย (p = 0.03–0.05) ≠ หยุดเทรด — แค่ใช้ robust z-score แทน

5.7 Crossing Statistics — วัดความถี่ Mean Reversion

แก่นความคิด
ADF บอกว่า ε กลับมาหา mean ในที่สุด — แต่ไม่บอกว่า บ่อยแค่ไหน Crossing Statistics ตอบคำถามนี้: ε ตัดผ่านเส้นกลางกี่ครั้งต่อหน่วยเวลา
E[Crossings] ≈ (1/π) · arccos(φ)

โดย φ คือ AR(1) coefficient จากการ regress ε_t บน ε_{t-1}:

ε_t = φ · ε_{t-1} + η_t, |φ| < 1 ความหมาย: φ ≈ 0 → E[Crossings] ≈ (1/π)·arccos(0) = 0.50/period ← ตัดถี่มาก (ดี) φ ≈ 0.65 → E[Crossings] ≈ (1/π)·arccos(0.65) ≈ 0.28/period φ ≈ 0.92 → E[Crossings] ≈ (1/π)·arccos(0.92) ≈ 0.13/period φ ≈ 1 → E[Crossings] → 0 ← ตัดน้อยมาก (ไม่ดี)
กฎง่ายๆ: φ น้อย = ดี เพราะ ε ตัดถี่

ยิ่ง φ ต่ำ ยิ่งมี trading opportunity มาก แต่ต้อง balance กับ Half-life:

  • φ ต่ำมาก (≈ 0) → ε เดินแบบ white noise → อาจ trade ไม่ทัน (spread กลับเร็วเกินจนจับไม่ได้)
  • φ สูง (≈ 0.99) → ε persistent มาก → กินทุน margin นาน → ไม่คุ้มค่า
  • Sweet spot: φ = 0.85–0.97 สำหรับ swing (daily, τ₁/₂ ≤ 24h), φ = 0.70–0.85 สำหรับ intraday

ความสัมพันธ์กับ Half-life

Crossing Statistics กับ Half-life บอกข้อมูลเดียวกันในมุมต่าง:

# Rolling ADF Monitor — รัน weekly หรือ daily ช่วง volatile
function rolling_adf_monitor(prices_A, prices_B, window=90, step=7):
  results = []
  i = window

  while i <= len(prices_A):
    # ใช้ข้อมูล window วันล่าสุด (rolling fixed)
    A_win = prices_A[i-window : i]
    B_win = prices_B[i-window : i]

    beta = ols_slope(log(B_win), log(A_win))
    eps = log(A_win) - beta * log(B_win)
    p = adf_test(eps).p_value

    if p < 0.05: status = "green"
    elif p < 0.08: status = "yellow" # ลด size 50%
    elif p < 0.10: status = "orange" # ห้ามเปิดใหม่
    else: status = "red" # ปิดทุก position

    results.append({"bar": i, "p": p, "beta": beta, "status": status})
    i += step

  return results

# ตรวจ trend ของ p-value — อันตรายที่ซ่อนอยู่
function detect_p_trend(results, lookback=4):
  p_recent = [r["p"] for r in results[-lookback:]]
  slope = ols_slope(range(lookback), p_recent)
  if slope > 0.005: # p เพิ่มขึ้น > 0.005 ต่อ step → deteriorating
    return "DETERIORATING" # เตือนแม้ p ยังอยู่ใน green zone
  return "STABLE"

5.10 Multiple Testing & Winner's Curse ใน Pair Scan

Funnel ใน §5.8 กรอง "100 → 3-5 คู่" — ตัวเลขนี้ฟังดูน่าเชื่อถือ แต่ซ่อนกับดักทางสถิติที่ร้ายแรง: การสแกนหลายคู่แล้วเลือกที่ดีที่สุด คือการทำ hypothesis test ซ้ำหลายครั้ง ซึ่งเปลี่ยนความหมายของ p-value ที่เห็นไปอย่างสิ้นเชิง

ADF p<0.05 ของคู่ที่ "ผ่าน" อาจเป็นแค่ผู้ชนะโดยบังเอิญ

รัน ADF ที่ α=0.05 กับคู่ที่เป็น random walk ล้วน (ไม่มี cointegration จริง) 100 คู่ → คาดว่าจะ "ผ่าน" ~5 คู่โดยบังเอิญ — ตรงกับ funnel ที่บอกว่า "กรอง 100 → 3-5 คู่" พอดี นั่นคือผลลัพธ์ที่ noise ล้วนก็สร้างได้ ถ้าเทรดคู่ปลอมเหล่านี้ spread คือ random walk → เดินหนีไม่กลับ → ขาดทุนแบบ divergence

Winner's Curse — คู่ที่ถูกเลือกดูดีเกินจริงเสมอ
แม้คู่ที่ cointegrate จริง คู่ที่ "ถูกเลือก" จาก scan คือคู่ที่ sample ช่วงนั้นดูดีเกินความจริงของมันเอง (post-selection bias) — κ, σ, ความถี่สัญญาณใน backtest จึงสูงกว่าที่จะเจอ live เสมอ (regression to the mean ของ performance)
# 1) รายงาน expected false positives ทุกครั้งที่สแกน expected_false_positives = N_pairs × α # 2) ใช้ Bonferroni หรือ Benjamini-Hochberg FDR เป็น gate แทน α เดี่ยวๆ Bonferroni: α_adjusted = α / N_pairs BH-FDR: เรียง p-value จากน้อยไปมาก แล้วหา threshold ที่ p_(i) ≤ (i/N) × q # 3) confirm คู่ที่ผ่านบน fresh holdout — ไม่ใช่ walk-forward ภายในคู่เดียวกัน # 4) บังคับ economic prior: ทำไมสองตัวนี้ควรผูกกันเชิงโครงสร้าง? # 5) หลังเลือกคู่แล้ว shrink คาดการณ์: ใช้ half-life/σ จากช่วง confirm ไม่ใช่ช่วง scan
ตัวอย่างหลัก: 200 คู่ Random Walk ล้วนๆ
สแกน 200 คู่ (สมมติว่าเป็น random walk ล้วน ไม่มี cointegration จริงสักคู่) ที่ α=0.05: คาดว่าจะ "ผ่าน ADF" ประมาณ 10 คู่ โดยบังเอิญล้วนๆ BH-FDR ที่ q=10% บน 200 คู่: ตัดเหลือเฉพาะ p ที่เล็กจริง — เช่น ตัวอันดับ 5 ต้องมี p < 0.0025 ถึงจะผ่าน (ไม่ใช่ p<0.05 แบบเดี่ยวๆ) → ถ้า pipeline ของคุณกรอง "100→3-5 คู่" โดยไม่ปรับ α ตามจำนวนคู่ที่สแกน ต้องสงสัยว่าคู่ที่ผ่านเป็น winner จริงหรือ winner โดยบังเอิญ
Economic Prior — เกราะป้องกันที่ดีที่สุด

คู่ที่มีแต่สถิติ (p-value สวย) แต่ไม่มีเหตุผลเชิงกลไกว่าทำไมควรผูกกันเชิงโครงสร้าง (venue เดียวกัน / underlying เดียวกัน / flow เดียวกัน) ให้ discount หนัก — สถิติอย่างเดียวไม่เคยพอ ต้องมีเรื่องเล่าเชิงเศรษฐศาสตร์รองรับเสมอก่อนเชื่อ p-value

5.11 Grid-Search Parameter Tuning = Multiple Testing บน Parameter

ปัญหาเดียวกับ §5.10 เกิดซ้ำอีกชั้นตอนจูน entry z / exit z / lookback window — การลอง config หลายสิบแบบแล้วเลือกตัวที่ Sharpe สูงสุด คือการทดสอบสมมติฐานซ้ำบนพารามิเตอร์ ไม่ใช่แค่บนคู่

Sharpe สูงสุดจาก Noise ล้วนๆ ก็สูงได้ตามสัดส่วนจำนวน Config

ลอง entry z ∈ {1.5, 2, 2.5} × exit z ∈ {0, 0.5, 1} × window ∈ {30, 60, 90} × TF 2 แบบ = 54 configs — ต่อให้กลยุทธ์ไม่มี edge เลย ค่า max ของ Sharpe จาก 54 การจับฉลากจะสูงตาม √(2·ln N) โดยประมาณ บนข้อมูล 1 ปี best-of-54 โชว์ Sharpe 1.5-2 ได้จาก noise ล้วน — เกณฑ์ "Sharpe > 2" ที่คนใช้คัดกลยุทธ์ ผ่านได้สบายด้วยความว่างเปล่า

E[max Sharpe จาก N configs สุ่มล้วน] ≈ √(2 · ln N / years) # ตัวอย่าง: 54 configs, ข้อมูล 1 ปี E[max Sharpe] ≈ √(2 × ln(54) / 1) ≈ 2.8 # กับดักซ้อน: ทดสอบ config ที่เลือกบน OOS หนึ่งช่วง ผลไม่ดี → "ปรับนิดหน่อย" → ทดสอบ OOS เดิมซ้ำ # ทำไม่กี่รอบ OOS ช่วงนั้นก็กลายเป็น in-sample ของกระบวนการเลือก — หมดความศักดิ์สิทธิ์
ป้องกัน: Nested Walk-Forward + Final Holdout
  1. นับ N_configs ที่เคยลองทั้งหมด (รวมที่ลองแล้วทิ้ง) — ใช้ Deflated Sharpe Ratio เทียบ max-of-N ของ noise เป็น benchmark ขั้นต่ำ
  2. เลือกพารามิเตอร์ด้วย nested walk-forward: จูนใน train, ประเมินใน validation, รายงานผลจาก test ที่แตะครั้งเดียว
  3. กัน final holdout ไว้แตะได้ครั้งเดียวในชีวิตของกลยุทธ์
  4. ชอบพารามิเตอร์ที่มาจากทฤษฎี (เช่น entry จาก breakeven formula ใน ch3 §3.4 + friction ใน ch19) มากกว่าจาก search — ยิ่ง search space เล็ก ยิ่งเชื่อผลได้
หมายเหตุ: ADF/Engle-Granger นี้ใช้ได้กับ F(·) อื่นเช่นกัน

ADF/Engle-Granger ตรวจ stationarity ของ ε ได้ไม่ว่า F(·) จะเป็นอะไร — สูตรและ critical values MacKinnon ไม่เปลี่ยน สิ่งที่ต้องระวัง: (1) sampling frequency ต่างกันมากระหว่างประเภท ε (funding spread สุ่มตัวอย่างทุกชั่วโมง vs log-price ทุกวินาที) ทำให้ effective sample size ต่างกันแม้ lookback window เท่ากัน (2) null hypothesis เดิม (มี unit root) ตีความแบบเดียวกันเป๊ะไม่ว่า F(·) จะเป็นอะไร แต่กับดักที่พบบ่อยคือ ε จาก American options (ch18 §18.9) ที่ไม่ใช่ point-target แบบเดียวกับ pair ราคาปกติ — ต้องตรวจ exercise style ก่อนสมมติว่า ε ควร mean-revert เข้าหา 0
