## 0. โจทย์ที่ผู้ใช้เคาะแล้ว (หลักการกำกับทุกการตัดสินใจ)

| ข้อ | สิ่งที่ต้องการ | สิ่งที่ **ห้าม** ทำ |
|---|---|---|
| 1 | อธิบายให้ง่าย เข้าใจ **logic** ได้ | ❌ ลดความเข้มข้น/ตัดเนื้อหาออกเพื่อให้ง่าย |
| 2 | สอนให้เข้าใจ **การทำงานของ function** ไม่ใช่ท่องว่าพิมพ์อะไร | ❌ ให้โค้ดสำเร็จแล้วบอก "รันได้แล้ว จบ" |
| 3 | ต่อยอด**คิดเป็น logic** เองได้ | ❌ สอนเป็นสูตรลอกตาม (recipe) |
| 4 | **เป็นมิตรกับมือใหม่** | ❌ สมมติว่าผู้อ่านรู้อยู่แล้ว |
| 5 | **มือโปรต้องไม่เบื่อ** | ❌ อธิบายซ้ำซากจนคนมีพื้นข้ามทั้งบท |

### 🔑 หลักคิดที่ทำให้ข้อ 4 กับ 5 ไม่ขัดกัน — "ชั้นการอ่าน" (layering)

"มือใหม่เข้าใจ" กับ "มือโปรไม่เบื่อ" **ไม่ใช่ trade-off** ถ้าเลิกมองว่าความง่ายคือการ*เจือจาง* แล้วมองว่าความง่ายคือการ*เพิ่มชั้นที่ข้ามได้*

```
ชั้น 1  🚶 อ่านโค้ดเป็นภาษาคน      ← มือใหม่เริ่มที่นี่ · มือโปรกวาดตาผ่าน 2 วิ
ชั้น 2  🤖 แกะทีละขั้น / ทำไมบรรทัดนี้จำเป็น
ชั้น 3  🧠 ทำไมไม่ทำแบบอื่น · trade-off · edge case  ← มือโปรมาอ่านชั้นนี้
ชั้น 4  ⚙️ กับดักที่มือโปรเองก็พลาด · ตัวเลข/ต้นทุนจริง
```

- มือใหม่: ชั้น 1→2 พอเดินได้ · ชั้น 3–4 ติดป้าย **[รอบสอง]** ไว้ให้ข้ามได้อย่างสบายใจ
- มือโปร: ข้ามชั้น 1 แต่**ชั้น 3–4 คือของที่เขาหาอ่าน** — นี่คือส่วนที่กันความเบื่อ
- ⚠️ ความเบื่อของมือโปรเกิดจาก "ไม่มีชั้น 3–4" มากกว่า "มีชั้น 1" — ดังนั้นทางแก้คือ **เติมชั้นลึก ไม่ใช่ตัดชั้นง่าย**

**กฎเหล็กของรอบปรับปรุงนี้: เพิ่มได้ ห้ามลด** — ทุก finding ต้องแก้ด้วยการ *เติมชั้นอธิบาย* หรือ *จัดชั้นใหม่* ห้ามแก้ด้วยการตัดเนื้อหาเทคนิคออก

## 3. แผนตรวจสอบทั้งเล่ม — คณะผู้เชี่ยวชาญ 6 เลนส์

ตาม `craft-standard.md` (รีวิวหลายเลนส์อิสระจับ error คนละแบบ) ปรับเลนส์ให้เข้ากับ**หนังสือสอนเขียนโค้ด** — เดิมออกแบบไว้สำหรับหนังสือทฤษฎี จึงเพิ่มเลนส์ที่ตำราทฤษฎีไม่มีคือ "โค้ดรันได้จริงไหม"

รันทีละเลนส์ ทั้ง 8 ไฟล์ บันทึก finding เป็น `[เลนส์][ความรุนแรง] ไฟล์:บรรทัด — อาการ → ทางแก้`
ความรุนแรง: **C**ritical (ผิด/รันไม่ได้/หลงทาง) · **M**oderate (เข้าใจผิดได้) · **N**it (ขัดตา)

### เลนส์ 1 — 🐍 โค้ดต้องรันได้จริง *(สำคัญสุด — ตำราโค้ดที่รันไม่ได้ = พังทั้งเล่ม)*
- **สกัดทุก snippet ออกมารันจริง** ในสภาพแวดล้อมสะอาด — ไม่ใช่อ่านตรวจด้วยตา
- เช็ค: import ครบไหม · ตัวแปรถูกนิยามก่อนใช้ไหม (snippet ต่อเนื่องข้ามกล่อง) · เวอร์ชัน API ยังถูกไหม (`pandas` deprecation เช่น `.append()`, `fillna(method=)` · `statsmodels` signature)
- `np.random.seed` ครบทุกที่ที่โชว์ `.output` ไหม — **ถ้า output ในหนังสือ reproduce ไม่ได้ ผู้อ่านจะคิดว่าตัวเองพิมพ์ผิด**
- ตัวเลขใน `.output` ตรงกับที่โค้ดคำนวณจริงไหม (บทเรียนจากเล่ม math: เคยเจอ Gamma=0.0151 ไม่ตรงโค้ด)
- ตัวอย่างที่ยกว่า "ผิด" (เช่น `shift(-1)`) ติดป้ายชัดว่าห้ามลอกไปใช้ไหม

### เลนส์ 2 — 📐 ความถูกต้องเชิง quant / สถิติ
- log return vs simple return ใช้ถูกที่ไหม · annualize ด้วย √252 ถูกบริบทไหม
- lookahead / survivorship / p-hacking — อ้างครบและไม่ขัดกันเองข้าม Part ไหม
- ADF/Johansen ตีความ p-value และ null hypothesis ถูกไหม (จุดที่ตำราพลาดบ่อยที่สุด)
- VaR/CVaR, Kelly, Sharpe — สูตรและคำเตือน sample size ถูกไหม
- fee/slippage/funding ในบทที่ 25 สมจริงไหม

### เลนส์ 3 — 🟢 มือใหม่ตามได้ไหม *(โจทย์ข้อ 1–4)*
- ไล่อ่านแบบ **"คนไม่เคยเขียนโค้ด"** ทีละบรรทัด หยุดทุกจุดที่ต้อง "เดา"
- ทุกแนวคิดใหม่ถูกอธิบาย**ก่อน**ใช้ไหม (พบแล้ว: `with` ถูกใช้ใน Part VI ก่อนสอน)
- โค้ดที่ยาว >10 บรรทัด มี 🚶 หรือ 🤖 กำกับไหม → **นี่คือเช็คลิสต์หลักของ finding ข้อ 2**
- error message ที่มือใหม่จะเจอจริง มีสอนอ่านไหม (`KeyError`, `SettingWithCopyWarning`, `NaN` เงียบ ๆ)
- ศัพท์ที่โยงไป glossary ได้ — ทำ cross-ref ไหม

### เลนส์ 4 — 🔵 มือโปรได้อะไร *(โจทย์ข้อ 5 — กันเบื่อ)*
ตรวจว่าแต่ละบทมี **"ของที่คนเขียนโค้ดเป็นแล้วยังไม่รู้"** อย่างน้อย 1 ชิ้น:
- **ทำไมไม่ทำแบบอื่น** — vectorized vs event-driven ต้องมีเหตุผลเชิงวิศวกรรม (ไม่ใช่ "ทำได้ 2 แบบ")
- **กับดักที่มือโปรก็พลาด** — pandas index alignment เงียบ ๆ · float กับ order size/tick size · timezone ใน timestamp exchange · `asyncio` blocking call หลุดเข้า event loop
- **ตัวเลขจริงจากสนาม** — latency, rate limit, ต้นทุนต่อ round trip
- **heuristic ระดับโต๊ะ** — "Sharpe > 2 ให้สงสัยว่าลืมต้นทุน" ประเภทนี้กระจายพอไหม
- ถ้าบทไหน**ไม่มีของชั้น 3–4 เลย** = จุดที่มือโปรจะเบื่อ → บันทึกเป็น finding

### เลนส์ 5 — 🧵 ความสอดคล้อง + คำสัญญา
- **คำสัญญาในเล่มถูกทำจริงไหม** (พบแล้ว: "ตารางเสียงอ่าน ใช้ตลอดทั้งเล่ม" แต่ไม่ทำ) — ไล่ทุกประโยคที่บอกว่า "Part ต่อไปจะ..." / "ใช้ทั้งเล่ม" แล้วเช็คว่าเกิดขึ้นจริง
- naming/notation เดียวกันทั้งเล่มไหม (`returns` vs `ret` vs `rets`, `signal` vs `position`)
- running example (vol mean-reversion) ต่อเนื่องจริงไหม หรือหลุดกลางทาง
- cross-ref: appendix เข้าถึงได้ไหม · โยงเล่ม `math-*` ที่มีเนื้อหาเดียวกันไหม (**Write Once** — เช่น cointegration มีทั้งที่นี่และ `math-part8`)
- **Part 0 ↔ Part II ซ้ำกันแค่ไหน** (สถิติทั้งคู่) — ควรเป็น "แนวคิด → โค้ด" ไม่ใช่เล่าใหม่

### เลนส์ 6 — 🇹🇭 ภาษา / typography / HTML
ตาม `style-guide.md`:
- รายการ ≥2 ข้อ ใช้ `<ul>/<ol>` จริง ไม่ใช่ `•` + `<br>` (ตัวการทำบรรทัดไทยตัดกลางคำ)
- `.fm` เก็บเฉพาะโค้ด ✅ ผ่านแล้ว (ตรวจ 0 จุด)
- เว้นวรรครอบคำอังกฤษ · em-dash ≤1/ประโยค · ประโยค ≤~2 บรรทัดจอ
- Thai line-break `<script>` ท้ายไฟล์ครบทุกไฟล์ไหม (ห้ามแก้เนื้อใน)
- HTML entity ใน code (`&lt;` `&gt;` `&amp;`) escape ถูกทุกที่ไหม — commit ก่อนหน้าเคยแก้เรื่องนี้ อาจมีตกค้าง
